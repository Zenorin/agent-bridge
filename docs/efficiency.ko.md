# agent-bridge 토큰 최적화 사용 안내

## 실행과 계획
역할 배정은 외부 `agent-workflows.json`, 실행 프로그램·adapter 설정은 외부 `bridge-execution.json`에서 관리한다. 내부 역할은 고정하지 않으며 계획의 역할명은 외부 역할 파일에서만 해석한다. 기존 실행 프로필·필수 훅은 유지되고, `file-check` 프로필은 `programs/check-files.mjs`를 절대경로 Node 실행 파일로 호출한다. 모델 설정은 자동 변경하지 않는다.

```sh
agent-bridge send-plan plan.json --workflow C:/workflows/agent-workflows.json
agent-bridge run --once --profiles C:/workflows/bridge-execution.json
agent-bridge usage --project P1
agent-bridge record-usage event.json
```

모든 명령에 `--db`를 지정할 수 있다. 쓰기가 필요하면 실행 명령에 `--allow-write`도 필요하다.

```json
{
  "project_id":"P1",
  "cwd":"C:/work/P1",
  "sender":"codex",
  "steps":[
    {"id":"source","workflow_role":"research","goal":"자료 분류","acceptance":["원본과 의견 구분"],"file_refs":["source.txt"]},
    {"id":"review","recipient":"claude-code","goal":"분류 결과 검수","acceptance":["필수 조건 검증"],"depends_on":["source"]}
  ]
}
```

계획은 의존 순서로 정렬해 원자적으로 등록한다. 같은 계획의 재제출은 중복 작업을 만들지 않으며, 다른 계획이 같은 작업 ID를 사용하면 오류가 난다.

## 원문·조건·검수 보존
`goal`과 `acceptance`는 축약하거나 삭제하지 않는다. 단일 작업의 `context_refs:[{"path":"source.txt","lines":"2-4"}]`는 해당 줄을 그대로 발췌하고 전체 원본 참조와 해시를 보존한다. 모델 요약기는 사용하지 않는다. 다만 선택한 구간이 업무에 충분한지는 프로그램이 의미론적으로 보장하지 못한다.

후속 단계에는 조건·발견사항·검증 범위의 근거를 포함한 이전 응답 전체를 전달한다. 선행 단계의 필수 조건이 `pass`와 근거를 갖추지 못하면 후속 단계는 기다린다. 발행 전 시도·해시를 재검증하며, 파일 변경이나 컨텍스트 버전 경합이 있으면 오래된 결과의 발행을 차단한다. 내장 Codex→Claude 독립 검수 체인은 캐시로 생략하지 않는다.

## 순수 작업 재사용
작업 JSON에 다음처럼 명시한다.

```json
"reuse":{"pure":true,"version":"contract-v1","files":["environment.json"],"env":["RENDER_MODE"]}
```

명시적으로 선언한 순수 작업과 별도 검증 단계의 결과를 재사용할 수 있다. 내장 독립 검수 체인은 재사용 대상에서 제외한다. 모든 조건이 완결된 성공 결과만 저장하며, 입력·목표·조건·모델·프로필·워크플로·선언한 환경 파일·작업자 환경변수가 같아야 한다. 실행 프로그램의 식별정보·코드 해시도 추적하고 기존 출력 해시가 유지되는지 확인한다.

환경변수는 셸 전체를 보지 않는다. 셸마다 바뀌는 변수 때문에 재사용이 맞지 않고, 시크릿 값이 지문에 섞이기 때문이다. 지문에 들어가는 것은 실행기 `env` 덮어쓰기, `reuse.env`에 적은 변수, 브리지 설정(`AGENT_BRIDGE_*`)과 클라이언트 설정 위치(`CODEX_HOME`, `CLAUDE_CONFIG_DIR`)뿐이다. 프로그램이 읽는 다른 변수는 `reuse.env`에 적어야 하며, 빠뜨리면 그 변수가 바뀌어도 이전 결과를 재사용한다.

파일·환경이 바뀌거나 조건·근거가 불완전하면 재실행한다. 재사용 응답은 `reused_from`, `reused_artifacts`로 원본 검수 근거와 출처를 유지하며 이번 시도의 `changed_files.reported`·`observed`·`outside_scope`는 각각 빈 배열이다. 웹 시세·시간 의존·외부 부작용 업무에는 `pure`를 선언하면 안 된다. 선언에서 빠진 숨은 의존성은 자동 검출하지 못한다. 무손실 보장은 원문 전달·기계적 검사 등 검증된 범위에 한정된다.

## 프로그램 실행과 검증 범위
단순 프로그램도 사용자가 선택한 외부 프로필의 adapter 명령만 실행하며 같은 작업함·범위·취소·입력검증을 사용한다. OS 샌드박스나 네트워크 차단을 추가 보장하지 않는다. 쓰기는 작업봉투의 `sandbox`·`write_files`와 실행기의 `--allow-write` 허용이 필요하며 프로그램 설정이 권한을 늘리지 않는다.

작업 봉투의 최소 선택 필드 예시는 `{"profile":"file-check","execution":{"adapter":"check-files"}}`이며, 입력 파일과 `goal`/`acceptance`는 기존 작업 봉투에 유지한다. 외부 adapter 설정의 `code_files`에 추가 라이브러리·스크립트 의존성을 선언할 수 있다. 변경 가능한 숨은 의존성을 누락하면 완전한 재사용 안전성을 보장할 수 없다.

`check-files`는 참조 파일을 실제로 읽고 해시를 계산한다. 정확히 ‘모든 참조 파일이 존재하고 요청된 해시와 일치한다.’라는 조건만 평가하고 다른 조건은 `unverified`로 남긴다. 시각 품질이나 사업상 주장은 인증하지 않는다.

## 실측과 집계 해석
2026-11-05 격리 실측에서 닫힌 Gemini 반복업무의 첫 실행은 입력 12,769·출력 172, 총 12,941토큰이었다. reasoning 19는 출력의 일부다. 동일 재요청은 추가 모델 토큰 0이었고 원본 조건과 acceptance 근거도 같았다. 실제 프로그램으로 실행한 파일 무결성 2단계도 원본을 바꾸지 않고 모든 필수 무결성 검사를 통과했으며 모델 호출은 0이었다. 후속 새 DB 재검증에서도 닫힌 동일 입력 반복 시험에서 추가 모델 토큰 13,012→0과 동일한 acceptance 근거를 확인했다. 이는 좁은 시험 사례이며 범용 절감률, 47쪽 덱 성능, 시각 검수 품질의 증명이 아니다.

2026-11-05 두 번째 실측은 같은 읽기 작업(파일 하나에서 수치 세 개 옮기기)을 Codex `gpt-6-luna`/low로 계약 없이 2회, 계약을 붙여 2회 번갈아 실행하고 Claude `claude-haiku-5-5`/low로 1회 실행했다. 5회 모두 `calls`의 호출 수와 최대 입력 토큰이 각 도구의 세션 기록과 정확히 일치했다. Codex는 매번 모델 호출 2회였고 호출 한 번의 입력이 약 25,000토큰이어서, 아주 작은 새 작업도 총 약 50,000토큰(그중 약 절반은 캐시)이 들었다. 계약을 붙이면 총량이 평균 49,969에서 52,115로 약 4% 늘었고(호출당 입력 약 1,000토큰, 회신 약 180토큰 증가), 시간은 평균 24.5초에서 29.5초가 되었다. 네 번 모두 수치를 정확히 옮겨 이 쉬운 작업에서는 품질 차이가 보이지 않았다. 표본이 작은 단일 작업 결과이며 큰 작업의 비율로 일반화하지 않는다.

시도마다 `calls`에 모델 호출 수(`model_calls`)와 호출 한 번의 최대 입력 토큰(`peak_call_input_tokens`, 캐시 포함)을 남긴다. 큰 사용량이 "많은 호출 × 큰 맥락"에서 왔는지 이 두 값으로 구분한다. Codex는 스레드 누적 사용량이 바뀐 횟수를, Claude는 응답 메시지 ID 수를, Gemini는 사용량이 붙은 `agent_response` 단계 수를 센다(Gemini의 호출 한 번 입력은 `input_tokens`에 `cache_read_tokens`를 더한 값). 사용량이 없는 응답 단계가 하나라도 있으면 호출 수가 모자랄 수 있어 그 시도의 `calls`는 `null`로 둔다. 프로그램 실행과 재사용은 0이다. Gemini 스트림 형식은 2026-11-05 `agy` 실제 호출로 확인했다(도구 호출 1회, 응답 단계 2개: 입력 12,478과 2,271+캐시 10,424). 프로젝트 집계의 `calls.model_calls.total`은 모든 시도의 호출 수를 알 때만 채워진다.

사용량은 고유 작업 시도별로 집계한다. Codex 캐시 입력은 입력의 부분집합이고 Claude는 입력·캐시 읽기·쓰기를 구분한다. Gemini는 제공자 보고 총량을 우선한다. 미보고 값은 `null`이며 캐시 쓰기 미보고를 0으로 보지 않는다. 알려진 합계와 누락 수를 표시하고 `thread_total` 스냅샷은 합산하지 않는다.

별도 작성기가 빠질 수 있어 프로젝트 집계는 `bridge-attempts-only`와 외부 미측정을 표시한다. `record-usage`에는 실제 측정값, 프로젝트·제공자·고유 `event_id`, `scope:"separate-process"`, 영수증 경로인 `source`를 기록한다. 같은 이벤트 ID의 중복 집계는 막지만 출처 경로 자체가 수치의 독립 검증은 아니다. 모든 외부 작성기를 자동 포착하지 않으며, 토큰 수로 API·구독 과금액이나 계정 한도 절감률을 추정하지 않는다.
